# 比赛演示场景需求说明

更新时间：2026-06-16

## 1. 文档目的

本文档用于明确当前比赛版本的主展示场景、系统闭环要求和实现边界。

当前项目不再继续扩展分散功能，而是围绕 3 个可现场演示、可形成闭环、可由现有硬件逐步落地的场景开展开发与联调：

1. 主动求助 / 模拟跌倒后的闭环响应
2. 长时间静止无响应的异常确认与升级
3. 断网或市电异常下的本地自治与日志补传

本文档优先服务于：

- 比赛现场演示
- 风险状态机设计
- TFT 页面与语音提示设计
- 事件日志设计
- Home Assistant / 服务器展示设计

当前版本的项目实现重点已经转向：

- 在线状态上报
- 远程展示与联动
- 本地确认与超时升级
- 事件日志与恢复补传

对于精确人体检测、复杂位置变化分析和高置信度异常识别，当前版本仅保留接口与后续演进空间，不作为近期第一优先级。

## 2. 项目展示定位

当前比赛版本建议定位为：

**面向独居老人场景的隐私优先型边缘自治异常响应系统**

当前展示形态可进一步表述为：

**面向居家看护场景的在线 IoT 闭环展示系统**

展示重点不是“单一传感器精确识别跌倒”，而是：

- 在非成像、弱依赖网络的条件下；
- 通过本地感知、状态机、确认机制和联动控制；
- 实现异常触发后的提示、确认、升级、记录和远程同步闭环。

## 3. 总体需求

### 3.1 总体闭环

三个演示场景应尽量共用同一套闭环流程：

```text
异常触发 -> 本地提示 -> 等待用户确认 -> 超时升级 -> 记录日志 -> 远程展示/补传
```

### 3.2 本地侧共同能力

比赛版本至少应具备以下本地能力：

- STM32 本地状态机运行
- TFT 显示当前状态、事件和提示信息
- 蜂鸣器或语音播报进行本地提醒
- 按钮确认输入
- 遥控触发输入
- 继电器或灯光联动反馈
- 本地事件日志记录

### 3.3 远程侧共同能力

比赛版本建议具备以下远程展示能力：

- MQTT 上报当前状态
- Home Assistant 展示当前风险等级和最近事件
- 服务器或上位侧保存关键事件记录
- 网络恢复后支持关键日志补传

### 3.4 统一状态建议

比赛版本建议优先实现以下状态：

- `NORMAL`
- `NOTICE`
- `WARNING`
- `ALARM`
- `NO_RESPONSE`
- `OFFLINE`
- `POWER_BACKUP`

说明：

- 这里的状态命名服务于演示闭环，不要求与后续论文版本完全一致。
- 如果后续引入更细粒度状态，可在保持演示逻辑不变的前提下扩展。

## 4. 场景一：主动求助 / 模拟跌倒后的闭环响应

### 4.1 场景目标

展示系统在用户主动触发异常事件后，能够快速完成本地告警、用户确认、远程展示和日志记录。

本场景的核心不是证明系统已经实现高精度跌倒识别，而是展示异常事件发生后的完整应急闭环。

### 4.2 触发方式

比赛版本允许以下任一方式触发：

- 遥控器触发“模拟跌倒/异常”
- 本地求助按钮触发
- 语音命令触发求助

其中：

- 遥控器或按钮应作为必备触发方式
- 语音触发可作为增强功能，不应成为唯一触发方式
- 遥控触发接口应纳入当前构建目标，而不是仅停留在后续设想

### 4.3 输入信息

本场景的输入信息包括：

- 触发源类型
- 触发时间
- 当前设备在线状态
- 当前本地风险等级

### 4.4 系统响应要求

触发后系统应执行以下动作：

1. TFT 切换到异常事件页面
2. 本地蜂鸣器鸣叫或语音播报提示
3. 灯光或继电器联动，形成可见反馈
4. 生成异常事件日志
5. 通过 MQTT / 服务器更新远程状态

### 4.5 用户确认要求

系统进入确认等待阶段后，应支持以下任一确认方式：

- 本地按钮确认“我没事”
- 语音确认“我没事/确认安全”

确认后系统应：

- 解除高等级告警
- 记录“已确认安全”
- 保留本次事件日志

### 4.6 超时升级要求

若在设定时间内未收到确认，系统应：

- 将风险等级升级
- 加强蜂鸣器、语音或灯光反馈
- 更新远程页面状态
- 记录“超时未响应”

### 4.7 成功判据

现场演示中，本场景至少应证明：

- 异常可被稳定触发
- 本地屏幕和提示会立即响应
- 用户确认后系统状态能恢复
- 无确认时系统能升级告警
- 日志中能看到本次事件

## 5. 场景二：长时间静止无响应的异常确认与升级

### 5.1 场景目标

展示系统基于非成像人体感知能力，对“人在家但长时间未移动”的异常情况进行确认和升级处理。

本场景用于体现项目的隐私优先、边缘自治和持续看护能力。

### 5.2 触发依据

比赛版本优先采用以下信息作为触发依据：

- 雷达 `presence`
- 雷达 `still seconds`
- 雷达 `motion score`

后续可加入但当前不强依赖：

- 手机蓝牙存在信息
- 家庭 Wi-Fi 接入信息

### 5.3 场景定义

当系统检测到以下条件时，应进入长时间静止监测流程：

- 当前检测到有人存在
- 在设定时间窗口内持续低运动或无运动
- 未出现明确的主动取消或恢复活动

### 5.4 系统响应要求

本场景建议采用分级处理：

1. 先进入观察态或提醒态
2. TFT 显示“检测到长时间未活动，请确认当前状态”
3. 本地进行较温和的蜂鸣或语音提醒
4. 记录进入该状态的时间和证据

### 5.5 用户确认要求

若用户在提醒后主动确认安全，系统应：

- 恢复到正常或低风险状态
- 记录“长时间静止但已确认安全”

### 5.6 升级要求

若在提醒后仍持续无人响应，系统应：

- 升级为 `NO_RESPONSE` 或高风险态
- 加强本地提示
- 更新远程状态
- 记录升级时间

### 5.7 成功判据

现场演示中，本场景至少应证明：

- 系统能基于久静进入异常确认流程
- 系统不会直接跳到最高告警，而是先询问确认
- 用户确认和无人响应两条路径都能走通
- 日志中能体现状态切换过程

## 6. 场景三：断网或市电异常下的本地自治与日志补传

### 6.1 场景目标

展示系统在网络异常或供电异常情况下，仍可保留本地核心看护能力，并在恢复后同步关键日志。

### 6.2 场景边界

本场景分为两种模式：

- `断网模式`：比赛版本应优先实现
- `市电异常模式`：仅在具备备用供电条件下展示

若当前硬件尚不具备备用供电，则不得把“完全断电后系统仍运行”作为已实现能力对外宣称。

### 6.3 断网模式需求

当 MQTT、服务器或局域网连接异常时，系统应：

- TFT 显示离线状态
- 本地仍保持状态机、显示、蜂鸣/语音、按钮确认和基础联动能力
- 将关键事件写入本地缓存
- 网络恢复后补传关键事件

### 6.4 市电异常模式需求

仅在具备备用电池或备用供电能力时，本模式才成立。

当市电异常时，系统应：

- 切换到备用供电或最小运行模式
- TFT 显示市电异常或备用电源状态
- 保留关键异常检测和本地提醒能力
- 记录进入备用模式的时间

比赛版本不要求在备用供电模式下维持所有高功耗外设长期运行。

### 6.5 离线期间的异常处理

在断网或供电异常期间，如果又触发新的异常事件，系统应：

- 本地继续执行提示、确认和升级闭环
- 将事件及处理结果写入本地日志
- 在恢复联网后补传这些关键记录

### 6.6 恢复后的处理要求

当网络恢复或系统回到正常供电后，系统应：

- 更新本地在线状态显示
- 发送离线期间积累的关键事件
- 在远程侧显示“离线期间发生过异常事件”或类似信息

### 6.7 成功判据

现场演示中，本场景至少应证明：

- 网络断开后本地闭环仍然有效
- 异常期间产生的关键事件不会丢失
- 网络恢复后远程侧能看到补传结果

## 7. 三个场景的公共日志要求

每个关键事件建议至少记录以下字段：

- `event_id`
- `event_type`
- `trigger_source`
- `start_time`
- `ack_time`
- `clear_time`
- `risk_before`
- `risk_after`
- `result`
- `network_state`
- `power_state`

比赛版本不要求一次性把所有日志字段都完整展示在前端，但主控和服务器设计应尽量预留这些字段。

## 8. 非目标说明

当前比赛版本明确不以以下目标作为必须完成项：

- 高精度真实跌倒识别
- 房间精细分区标定
- 精确人体位置变化检测
- 生命体征检测
- 开放式自由对话语音助手
- 云端大模型实时控制主闭环

这些方向可作为后续演进路线，但不应影响当前 3 个主展示场景的落地。

## 9. 开发优先级建议

当前建议按以下优先级推进：

1. 完成三场景共用的本地状态机、提示、确认和日志框架
2. 先跑通场景一的稳定触发与确认闭环
3. 在同一状态机上补齐场景二的久静逻辑
4. 最后补场景三的离线缓存和恢复补传

同时要求：

- 遥控触发接口在比赛版本中优先落地，用于保证场景一现场可重复演示
- 低功耗设计从当前阶段起纳入后续开发计划，新增模块应评估是否影响最小运行模式、离线保活和备用供电演进

原因：

- 场景一最容易稳定展示
- 场景二最能体现项目核心价值
- 场景三最能体现边缘自治和工程深度

## 10. 一句话总结

比赛版本的重点不是扩展更多功能点，而是围绕“主动求助、久静无响应、断网/供电异常”三个场景，把异常触发后的本地提示、用户确认、超时升级、日志记录和远程同步闭环做完整。
