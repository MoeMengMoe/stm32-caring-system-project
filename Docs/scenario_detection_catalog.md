# 场景检测路线表

更新时间：2026-07-06

## 1. 为什么先做这张表

本项目是 AI+IoT 老人居家管理节点，不是单点传感器报警器。后续确实可以参考很多开源算法，例如视觉摔倒检测、IMU 跌倒检测、毫米波人体行为识别等；但这些算法必须先匹配我们的传感器数据。

当前 STM32 侧主要数据来自：

- Rd-03 V2：presence、distance_cm、zone、motion_score、energy_sum、still_seconds、occupied_seconds。
- PIR：有人活动数字量。
- BME280：温度、湿度、气压。
- MQ：gas_ppm_est、gas_delta_mv、baseline。
- SOS/ACK：本地人工确认。
- ESP8266/云端：状态上报、事件上报、远程指令。
- 继电器/蜂鸣器/TFT：本地执行和展示。

所以现阶段最重要的不是盲目增加模型，而是把“能稳定检测什么、怎么验收、后续 AI 吃什么数据”定义清楚。

## 2. 当前可以直接做的核心场景

| 场景 | 当前状态 | 主要数据 | 第一版判断 | 执行动作 | 验收方式 |
|---|---|---|---|---|---|
| 主动求助 / 模拟跌倒 | 已接入 | SOS 按钮、云端 D 命令 | 用户主动触发或远程模拟触发 | 进入 ACK_WAIT，蜂鸣器提醒，继电器告警灯，事件上报 | 按 SOS 或发 `1`，再按 ACK/clear |
| 长时间静止无响应 | 已接入第一版 | radar_presence、still_seconds、motion_score、ACK | 有人存在且长时间低运动，进入确认流程 | 提醒、等待 ACK、超时升级 | 人保持静止，观察 still_seconds 和状态迁移 |
| 气体风险 | 已接入第一版 | gas_ppm_est、gas_delta_mv、baseline | ppm 估算超过阈值进入确认流程 | 提醒、上报、联动继电器 | 串口发 `3` 或后续用气体源验证 |
| 断网本地自治 | 已接入第一版 | network_state、relay_auto_mask、event cache | 网络离线仍能本地告警和继电器动作 | relay2 离线灯、事件缓存 | 串口 `o/n` 模拟离线/在线 |
| 远程控制本地负载 | 已接入 | ESP8266 命令、relay mask | 云端/Simon 端控制继电器 | LED 负载亮灭，本地 ACK 可清除 | Simon 下发命令，本地 ACK 复位 |

## 3. 建议马上新增/强化的场景

### 3.1 离床 / 离开房间过久

可行度：高。

当前 Rd-03 能提供 presence、distance_cm 和 occupied_seconds。我们可以先做一个“区域粗分类”版本：

- near zone：床边/桌边/近距离活动。
- mid zone：房间中部活动。
- far zone：远距离活动。
- none：无人。

第一版规则：

```text
之前有人 -> presence 变 0 持续一段时间 -> 标记为离开
夜间或护理模式下离开过久 -> NOTICE / WARNING
离开后无 ACK 或无返回 -> 上报事件
```

注意：这不是精确定位，只是居家看护中的“活动状态解释”。

### 3.2 夜间异常活动

可行度：中高。

需要增加一个简单时间上下文。没有 RTC 时，可以先用“演示模式”命令模拟夜间；有云端后由云端下发当前时间段。

第一版规则：

```text
night_mode=1
presence/motion 频繁变化
或离床持续时间过长
-> NIGHT_ACTIVITY_NOTICE
```

这个场景很适合 AI+IoT 展示，因为云端可以结合历史作息做解释。

### 3.3 环境舒适度风险

可行度：高。

使用 BME280 + MQ：

```text
温度过高 / 湿度过高 / 气体 ppm 升高
-> ENV_COMFORT_NOTICE
严重时 -> GAS_RISK 或 ENV_RISK
```

这是低风险但展示效果好的场景，适合 TFT 和 Home Assistant 面板。

### 3.4 无响应升级

可行度：高。

这不是新传感器，而是把现有状态机做得更像产品：

```text
进入 ACK_WAIT
本地蜂鸣器提醒
若 ACK 超时
-> ESCALATED
-> 云端通知 / 继电器更明显联动 / 语音模块后续接入
```

这个场景是答辩时最容易讲清楚的闭环。

## 4. 关于“老人跌倒检测”

真正的跌倒检测分几类：

| 路线 | 典型输入 | 优点 | 当前限制 | 我们的策略 |
|---|---|---|---|---|
| 视觉姿态检测 | 摄像头、人体关键点 | 成熟、开源多、直观 | 当前 STM32 侧无摄像头，隐私和算力要处理 | 后续作为云端/视觉辅助验证 |
| 穿戴式 IMU | 加速度、陀螺仪 | 对跌倒敏感 | 需要老人佩戴设备 | 后续可作为扩展，不作为当前主线 |
| 高级毫米波点云雷达 | 点云、速度、姿态特征 | 隐私好，适合室内 | Rd-03 V2 输出不是完整点云 | 当前只能做跌倒“疑似/确认流程” |
| 多传感器规则融合 | 雷达、PIR、按钮、环境、ACK | 适合当前硬件，闭环强 | 不是医学级跌倒识别 | 作为当前主线 |

因此当前不要宣传“已准确识别老人跌倒”。更稳妥的说法是：

```text
系统支持主动求助、模拟跌倒事件、长时间静止无响应确认、
以及基于雷达/环境/人工确认的异常风险闭环。
后续视觉或更高级雷达可作为跌倒识别增强模块接入。
```

这样既不虚，又能把 AI+IoT 的扩展空间讲出来。

## 5. AI 数据采样层

从 2026-07-06 起，主控会周期输出：

```text
[AI_SAMPLE] t=... temp=... hum=... gas_ppm=... gas_delta=... presence=... radar_valid=... radar_presence=... radar_cm=... zone=... motion=... energy=... still=... occupied=... state=... scenario=... risk=...
```

这个日志不是给人肉长期看的，而是给后续数据集和 AI 使用的。建议以后每次做场景实验时保存 COM6 日志，并在文件名里写清楚场景，例如：

```text
ai_sample_long_still_20260706.log
ai_sample_leave_bed_20260706.log
ai_sample_gas_risk_demo_20260706.log
```

后续云端或 Python 脚本可以把这些日志转成 CSV，再做阈值调参、决策树、轻量模型或云端 AI 分析。

## 6. 推荐下一步

短期不建议马上塞开源模型。推荐顺序：

1. 先烧录当前版本，确认 `[AI_SAMPLE]` 每 2 秒输出一次。
2. 做三组真实日志：正常活动、长时间静止、离开/返回。
3. 基于日志调 `still_seconds / motion_score / zone` 阈值。
4. 增加 `LEAVE_BED_OR_ROOM` 场景。
5. 再增加 `NIGHT_ACTIVITY_NOTICE` 和 `ENV_COMFORT_NOTICE`。
6. 等云端日志稳定后，再让云端 AI 做“风险解释”和“趋势总结”。
